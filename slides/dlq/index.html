DLQ คืออะไร?

🏭 เปรียบเหมือนสายพานโรงงาน
ชิ้นงานที่ตรวจแล้วไม่ผ่านซ้ำๆ จะถูกแยกไปไว้ที่ "ตะกร้าของเสีย" ต่างหาก
ไม่ปล่อยให้ขวางสายพานหลักจนชิ้นงานอื่นเดินต่อไม่ได้

Dead Letter Queue คือที่พักของ message ที่ประมวลผลไม่สำเร็จซ้ำแล้วซ้ำเล่า

แทนที่จะปล่อยให้ หายไปเงียบๆ หรือ วนกลับเข้าคิวหลักไม่รู้จบ

    C -->|สำเร็จ ✓| D[Ack ปิดงาน]
    C -->|ล้มเหลว| E[Retry + Backoff]
    E -->|ยังไม่ครบ max retry| B
    E -->|เกิน max retry| F[Dead Letter Queue]

Fixed delay (2s คงที่) Exponential backoff (1→2→4→8→16→32s)
💡 หากมี client จำนวนมาก retry พร้อมกัน ต้องเพิ่ม Jitter (สุ่มปรับเวลาขึ้น-ลง) เพื่อกระจาย load ไม่ให้ชน spike

Permanent vs Transient Error

⚡ Transient Error

Network timeout, downstream โหลดสูงชั่วคราว

→ รอ backoff แล้ว retry ใหม่

🚫 Permanent Error

Data ผิดรูปแบบ, schema ไม่ตรง

→ Fail fast เข้า DLQ ทันที

⚖️ Max Retry Count ต้องสมดุล
น้อยไป → ตัด transient error ก่อนเวลา  |  มากไป → ตรวจพบ bug ช้า

ตั้งค่าใน Broker แต่ละตัว

Broker วิธีตั้งค่า DLQ วิธี Delay Retry
RabbitMQ x-dead-letter-exchange / x-dead-letter-routing-key Retry queue ตั้ง TTL แล้ว dead-letter กลับ main queue อัตโนมัติ
AWS SQS Redrive Policy + maxReceiveCount ควบคุมผ่าน visibility timeout
Kafka ไม่มีในตัว — produce ไป topic แยก เช่น orders.DLQ เขียน consumer แยกที่ sleep ก่อน produce กลับ
Azure SB MaxDeliveryCount + DeadLetterAsync() ควบคุมผ่าน lock duration

🔄 Idempotency เช็ค message ID ก่อน process ป้องกัน side effect ซ้ำ
🤖 Automated Redrive สำหรับ transient error ที่รู้แน่ว่าจะหายเอง
📊 Dashboard แยกตาม error type เพื่อเห็น pattern เร็วขึ้น

สรุปสั้นๆ ที่ต้องจำ

  • DLQ กันไม่ให้ poison message ขวางคิวหลัก และกันไม่ให้ message หายไปเงียบๆ
  • Backoff ต้องเพิ่มเวลารอแบบ exponential ยิ่งดีถ้ามี jitter ด้วย
  • Permanent error ควร fail fast เข้า DLQ ทันที ไม่ต้อง retry ให้เสียเวลา
  • Max retry count ต้องสมดุล — น้อยไปตัด transient, มากไปตรวจพบ bug ช้า
  • Consumer ต้อง idempotent เสมอ เพราะ redrive มีโอกาส process ซ้ำ
